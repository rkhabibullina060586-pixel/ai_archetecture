## Тема

Машиностроительная промышленность: платформа с использованием ИИ для определения
неисправностей и планирования обслуживания на основе данных машинного обучения —
**до того**, как неисправность привела к остановке и замене оборудования.

## Бизнес-задача

Отказ оборудования на машиностроительном предприятии означает незапланированный
простой, срыв сроков заказов и дорогой аварийный ремонт. Реактивное обслуживание
(«ремонтируем после поломки») и регламентное («обслуживаем по расписанию»)
одинаково неэффективны.

**Решение:** AI-платформа предиктивного обслуживания, которая по данным
IoT-телеметрии оценивает вероятность отказа заранее и позволяет перейти к
обслуживанию по фактическому прогнозируемому состоянию оборудования.

## Задача машинного обучения

| Параметр | Значение |
|---|---|
| Тип задачи | бинарная классификация |
| Целевая переменная | `failure_next_24h` |
| Горизонт прогноза | 24 часа |
| Объект наблюдения | одна машина × один час |
| Объём выборки | 17 572 наблюдения |
| Доля положительного класса | 2,96 % (несбалансированная задача) |
| Метрики качества | Recall, Precision, F1, ROC-AUC, PR-AUC |

**Признаки:** часовые агрегаты IoT-телеметрии — `mean` / `max` / `std`
по температуре, вибрации и энергопотреблению (9 признаков), а также
производные признаки динамики (скользящее среднее, отклонение от него,
z-оценка относительно индивидуальной нормы машины).

## Ключевые методические решения

**Агрегация на стороне СУБД.** 2,29 млн измерений сворачиваются в часовые окна
внутри `VIEW` через `AGG(...) FILTER (WHERE ...)` — в Python приходит уже готовый
аналитический датасет вместо сырой телеметрии.

**Защита от утечки целевой переменной.** Окно разметки строго в будущем
относительно момента наблюдения (`failure_time > observation_hour`), а разбиение
на train/test — по времени, а не случайное: соседние часы одной машины почти
идентичны, и случайный split завысил бы метрики.

**Пропуски — двухэтапное заполнение.** Сначала медиана по конкретной машине
(у разных машин разные нормальные режимы), затем общая медиана как резерв.
Дополнительно сохраняются флаги `*_was_missing`: отсутствие измерения само
по себе может означать неисправность сенсора.

**Выбросы — ограничение, а не удаление.** Границы по правилу IQR
(`Q1 − 1,5·IQR`, `Q3 + 1,5·IQR`), но применяется winsorization (clipping).
Экстремальное значение в промышленных данных может быть реальным признаком
приближающейся неисправности — удалять такие наблюдения значит выбрасывать
именно те строки, ради которых строится модель.

**Некорректные значения** отсекаются на уровне SQL: записи с
`quality_status = 'MISSING'` не попадают в представление.

## Проверяемые гипотезы

| № | Гипотеза | Признаки | Ожидаемая связь |
|---|---|---|---|
| 1 | Рост температуры повышает вероятность отказа | `mean_temperature`, `max_temperature` | возрастающая, с порогом |
| 2 | Повышенная вибрация — индикатор механической неисправности | `mean_vibration`, `max_vibration`, `std_vibration` | возрастающая, сильнее по пикам |
| 3 | Нестабильность температуры повышает вероятность отказа | `std_temperature` | возрастающая |
| 4 | Риск зависит от индивидуальных характеристик машины | `machine_id` | неоднородность парка |

Каждая гипотеза проверяется U-критерием Манна–Уитни, точечно-бисериальной
корреляцией и размером эффекта Cliff's delta; гипотеза №4 — критерием хи-квадрат.

## Основные выводы

1. Задача сильно несбалансирована (2,96 % положительного класса), поэтому
   `Accuracy` неинформативна — используются `Recall` и `PR-AUC`.
2. Ни один усреднённый параметр сам по себе не объясняет отказ: линейные
   корреляции с целевой переменной слабые. Зависимость нелинейная, временная
   и комбинированная.
3. Динамика информативнее уровня: признаки разброса, пиков и отклонения от
   индивидуальной нормы машины дают больше, чем простые средние.
4. Абсолютные пороги для всего парка оборудования неприменимы — нужны
   индивидуальные нормы по каждой машине.

## Направления развития

* признаки оборудования: `machine_type`, `machine_age`, `nominal_power_kw`,
  наработка с последнего обслуживания из `maintenance_work_orders`;
* окна агрегации 6 / 24 / 72 часа, тренды и скорости изменения;
* градиентный бустинг и калибровка вероятностей;
* выбор порога по экономике: стоимость простоя против стоимости лишней диагностики;
* объяснимость (SHAP) — платформа должна указывать, **какой** параметр вызвал
  тревогу, иначе служба эксплуатации не будет доверять прогнозу.
