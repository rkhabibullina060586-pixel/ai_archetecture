## Тема

Машиностроительная промышленность: платформа с использованием ИИ для определения
неисправностей и планирования обслуживания на основе данных машинного обучения —
**до** того, как неисправность привела к остановке и замене оборудования.

## Бизнес-задача

Отказ оборудования означает незапланированный простой, срыв сроков заказов и
дорогой аварийный ремонт. Реактивное обслуживание («ремонтируем после поломки»)
и регламентное («обслуживаем по расписанию») одинаково неэффективны.

**Решение:** AI-платформа предиктивного обслуживания, которая по данным
IoT-телеметрии оценивает вероятность отказа заранее и позволяет перейти к
обслуживанию по фактическому прогнозируемому состоянию оборудования.

## Задача машинного обучения

| Параметр | Значение |
|---|---|
| Тип задачи | бинарная классификация |
| Целевая переменная | `failure_next_24h` |
| Горизонт прогноза | 24 часа |
| Объект наблюдения | одна машина × один час |
| Объём выборки | 17 572 наблюдения |
| Доля положительного класса | ≈ 3 % (несбалансированная задача) |
| Метрики | Recall, Precision, F1, ROC-AUC |

**Признаки:** часовые агрегаты IoT-телеметрии — `mean` / `max` / `std` по
температуре, вибрации и энергопотреблению (9 признаков), плюс производные
признаки динамики: скользящее среднее за 6 часов, отклонение от него и
z-оценка относительно индивидуальной нормы машины.

## Ключевые методические решения

**Агрегация на стороне СУБД.** 2,29 млн измерений сворачиваются в часовые окна
внутри `VIEW` через `AGG(...) FILTER (WHERE ...)` — в Python приходит готовый
аналитический датасет вместо сырой телеметрии.

**Защита от утечки целевой переменной.** Окно разметки строго в будущем
относительно момента наблюдения (`failure_time > observation_hour`).

**Разбиение по времени, а не случайное.** Соседние часы одной машины почти
идентичны, поэтому при случайном `train_test_split` почти каждое тестовое
наблюдение имело бы «двойника» в обучающей выборке и метрики оказались бы
завышенными. Модель обучается на раннем периоде и проверяется на позднем.

**Пропуски — двухэтапное заполнение.** Сначала медиана по конкретной машине
(у разных машин разные нормальные режимы), затем общая медиана как резерв.
Дополнительно сохраняются флаги `*_was_missing`: отсутствие измерения само по
себе может означать неисправность сенсора.

**Выбросы — ограничение, а не удаление.** Границы по правилу IQR
(`Q1 − 1,5·IQR`, `Q3 + 1,5·IQR`), применяется winsorization. Экстремальное
значение в промышленных данных может быть реальным признаком приближающейся
неисправности — удалять такие наблюдения значит выбрасывать именно те строки,
ради которых строится модель.

**Некорректные значения** отсекаются на уровне SQL: записи с
`quality_status = 'MISSING'` не попадают в представление.

**Подбор порога вместо порога 0.5.** При 3 % положительного класса `Accuracy`
бесполезна, а порог 0.5 даёт низкую полноту. Порог снижается осознанно:
пропущенный отказ дороже ложной тревоги.

## Проверяемые гипотезы

| № | Гипотеза | Признаки | Ожидаемая связь |
|---|---|---|---|
| 1 | Рост температуры повышает вероятность отказа | `mean_temperature`, `max_temperature` | возрастающая, с порогом |
| 2 | Повышенная вибрация — индикатор механической неисправности | `mean_vibration`, `max_vibration`, `std_vibration` | возрастающая, сильнее по пикам |
| 3 | Нестабильность температуры повышает вероятность отказа | `std_temperature` | возрастающая |
| 4 | Риск зависит от конкретной машины | `machine_id` | неоднородность парка |

Гипотезы проверяются долей отказов по квантильным интервалам признаков
(`pd.qcut`) — такой подход показывает и нелинейную связь, которую коэффициент
корреляции не улавливает.

## Основные выводы

1. Задача сильно несбалансирована, поэтому `Accuracy` неинформативна —
   используются `Recall` и `F1`, порог подбирается отдельно.
2. Ни один усреднённый параметр сам по себе не объясняет отказ: линейные
   корреляции с целевой переменной слабые. Зависимость нелинейная, временная
   и комбинированная.
3. Динамика информативнее уровня: разброс, пики и отклонение от индивидуальной
   нормы машины дают больше, чем простые средние.
4. Абсолютные пороги для всего парка неприменимы — нужны индивидуальные нормы.

## Направления развития

* признаки оборудования: тип, возраст, номинальная мощность, наработка с
  последнего обслуживания из `maintenance_work_orders`;
* окна агрегации 6 / 24 / 72 часа, тренды и скорости изменения;
* другие алгоритмы классификации и подбор гиперпараметров кросс-валидацией
  с учётом временной структуры данных;
* метрика `PR-AUC` — для сильного дисбаланса информативнее `ROC-AUC`;
* выбор порога по экономике: стоимость простоя против стоимости диагностики;
* объяснимость прогноза — платформа должна указывать, **какой** параметр
  вызвал тревогу.
